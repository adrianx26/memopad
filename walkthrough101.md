# MemGraphRAG Phase 2 Walkthrough

## Overview
I have continued the implementation of the MemGraphRAG feature by completing Phase 2: **Conflict Detection & Schema Normalization**. These changes ensure that knowledge extracted by the LLM remains consistent and that contradictory facts are flagged for resolution instead of silently polluting the context window.

## Changes Made

### 1. Schema Normalization (`SchemaService`)
- Added `SchemaService` to track and normalize categories generated by the LLM.
- **Noise Reduction**: Unifies inconsistent casing or naming (e.g., `Status`, `status`, `STATUS`) into canonical categories based on frequency.
- **Integration**: Wired into `EntityService.update_entity_and_observations`. When new observations are saved, their categories are first run through `SchemaService.normalize_category`.
- **Database Tracking**: Added `ObservationSchema` model and `ObservationSchemaRepository` to store schema definitions and aliases.

### 2. Conflict Detection (`ConflictService`)
- Implemented `ConflictService` to flag divergent observations on the same entity and category.
- **Detection Logic**: Uses `difflib.SequenceMatcher` to calculate a similarity ratio. If the similarity is low, a conflict is raised.
- **Bidirectional Linking**: Updates the `conflict_score`, `conflicting_obs_id`, and `conflict_resolved` fields on both sides of a conflicting pair.
- **Provenance**: Records the `provenance_path` to track exactly which source file originated the observation.
- **Integration**: Wired into `EntityService.update_entity_and_observations` to automatically trigger detection after saving new observations.

### 3. Database Migrations
- Two Alembic migrations have been configured to support these new models:
  - `h1b2c3d4e5f6_add_observation_conflict_fields.py`: Extends the `observation` table.
  - `i2c3d4e5f6a7_add_observation_schema_table.py`: Creates the `observation_schema` and `observation_schema_alias` tables.

### 4. API & Tool Context
- `ObservationSummary` schema and `GraphContext` now expose `conflict_score`.
- LLMs consuming the `search_notes` and `build_context` MCP tools will now see these conflict markers naturally serialized in their context graphs, prompting them to resolve contradictions.

## Testing & Validation
- **Unit Tests**: Created `test_schema_service.py` to achieve 100% test coverage on `SchemaService`.
- **Type Checking**: Resolved all `pyright` and `ruff` linting issues related to the new services and repository dependencies.
- **Test Suite**: Verified `EntityService` tests and corrected failing API assertions in `test_knowledge_router.py`.

## Next Steps (Phase 3 & 4)
With Conflict Detection and Schema Normalization complete, the system now maintains a clean and consistent knowledge graph. The next phases involve refining prompt instructions to guide the LLM on how to resolve conflicts and utilizing these new fields for advanced context curation.
